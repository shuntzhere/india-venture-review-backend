---

## Objective

Add a `classification_confidence` column to the existing `funding_events` table to support the morning review workflow where articles are prioritised by classifier confidence before manual research and content creation begins. This column stores operational metadata produced by the classifier introduced in Step 3.2, not a business property of the funding event itself.

## Technical Decisions

**`classification_confidence` rather than `confidence_level`**
The column name `confidence_level` would suggest a property of the funding event itself — how certain we are that it is a real event. The chosen name `classification_confidence` makes explicit that this is the classifier's assessment of the article at ingestion time. It is metadata about the classification process, not about the event.

**Nullable by design**
The column allows NULL for two reasons. First, existing rows in `funding_events` were inserted before the classifier existed and have no classification assessment — making the column NOT NULL would require backfilling every row before the migration could run. Second, future classifier versions may not populate this field immediately during a migration window. NULL has a distinct semantic meaning here: "not yet assessed by the classifier", which is different from "Weak" (assessed and low confidence).

**CHECK constraint over an ENUM type**
A PostgreSQL `ENUM` type would also restrict values, but ALTERing an ENUM to add new values requires a schema migration and carries risk in production. A `TEXT` column with a `CHECK` constraint is simpler to extend: adding a new confidence tier (e.g. `"Very Strong"`) requires only updating the constraint, not modifying a type definition. The constraint also reads clearly in `information_schema` queries.

**PostgreSQL NULL behaviour with CHECK and IN**
In PostgreSQL, `NULL IN ('Strong', 'Moderate', 'Weak')` evaluates to NULL — not FALSE. CHECK constraints only reject a row when the condition evaluates to FALSE. NULL evaluates as passing. This means the `IN (...)` constraint implicitly permits NULL without requiring an explicit `OR classification_confidence IS NULL` clause. This behaviour is documented in the migration file as a comment for future readers.

**Separate migration file — never modify `create_tables.sql`**
`sql/create_tables.sql` represents the initial schema as it was deployed. Modifying it after deployment would create a mismatch between the file and the actual database state for anyone who already ran it. Each subsequent schema change gets its own numbered migration file (`add_classification_confidence.sql`). This is standard migration practice and ensures the SQL folder is a reliable audit trail of every schema change in order.

**This is operational metadata, not business data**
`classification_confidence` describes how confident the classifier was when it ingested the article — not a property of the funding event itself. The classifier's assessment may change if the article is re-classified by a future version. Storing it in `funding_events` is correct because it is attached to the ingestion record, but it should be understood as pipeline metadata rather than ground truth about the funding event.
