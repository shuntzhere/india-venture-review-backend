# Step 3.2: Funding Article Classifier v1

Evolved the funding classifier from a keyword matcher into a weighted multi-signal scoring engine with an extensible registry pattern.

---

## Objective

Replace the single-function keyword classifier with a two-layer architecture: independent signal detectors and a classification engine. Introduce three signals (funding keyword, funding amount, investor phrase), a weighted scoring system, and a `SIGNAL_REGISTRY` pattern that allows new signals to be added by registering one tuple. The public interface of `fetch_entrackr_articles()` must remain unchanged.

## Technical Decisions

**Two-layer architecture: signal detection separated from classification engine**
The original `is_funding_article()` combined detection and decision-making in one function. The new architecture separates these concerns completely. Signal detectors (`detect_funding_keyword`, `detect_funding_amount`, `detect_investor_phrase`) each take `(title, content)` and return a plain boolean — they have no knowledge of weights, thresholds, or each other. `classify_article()` is the only function that knows about scoring — it iterates the registry, sums weights, and decides. This means either layer can be changed independently without affecting the other.

**`SIGNAL_REGISTRY` pattern**
The registry is a list of `(signal_name, detector_fn, weight)` tuples. `classify_article()` iterates this list — it never calls any detector directly by name. To add a new signal, a developer writes one function and appends one tuple. No other code changes. This is a deliberate design choice: the registry is the single place that defines what signals exist and how much they contribute. Future signals (valuation detection, company entity detection, AI classifier) follow the same pattern with no structural changes to the engine.

**Weights and threshold: `funding_keyword +3`, `funding_amount +2`, `investor_phrase +1`, threshold `3`**
The prompt suggested weights of +2/+2/+1 with threshold 2. This was adjusted before implementation for an important reason: with those values, a funding amount alone (score 2) would equal the threshold, meaning revenue-reporting articles containing dollar figures (e.g. `"Prosus India posts $781 Mn revenue in FY26"`) would be accepted as funding events. By raising the keyword weight to +3 and the threshold to 3, a keyword alone is sufficient (3 ≥ 3) while an amount alone is not (2 < 3). This prevents the most common false positive class — financial performance articles — without reducing recall for actual funding events, which almost always contain a keyword.

**Content extracted before classification**
In Step 3.1, HTML cleaning was applied after the keyword check. In Step 3.2, the two content-based signals (funding_amount, investor_phrase) need to search the article body — not just the title. The extraction and HTML stripping steps were therefore moved before `classify_article()` is called. This is a necessary sequencing change: the classifier receives clean text for all signals.

**`classify_article()` returns a structured dict, not a boolean**
The classifier returns `{"accepted": bool, "score": int, "signals": list}`. This structured result is used internally: the `accepted` field drives the accept/reject decision; `score` and `signals` drive the verbose output. The public interface (`fetch_entrackr_articles()` return value) is unchanged — score and signals are never included in the returned article dicts.

**Confidence labels: `Strong`, `Moderate`, `Weak`**
Labels are derived from the score in `_confidence_label()`, a separate helper function. `score >= 5` is Strong (keyword + amount, or all three signals); `score >= 3` is Moderate (threshold met but not strongly); below threshold is Weak. Labels exist only in the verbose validation output — the classifier makes all decisions using the numeric score and threshold, not the label. This keeps the labels as a developer diagnostic tool rather than a classification mechanism.

**Known edge case: Turtlemint IPO listing (Moderate, false positive)**
`"Turtlemint lists at 11.25% discount on market debut"` was accepted at Moderate (score 3) because the article body contained a share price in Rupees (triggering `funding_amount`) and the phrase `"backed by"` somewhere in the content (triggering `investor_phrase`). The article is an IPO listing story, not a funding event. This edge case was documented rather than fixed because: (a) it scores Moderate rather than Strong, indicating genuine classifier uncertainty; (b) the correct resolution is to filter it in the parser (Step 4) where full article content is available; (c) fixing it at the classifier layer would require special-casing IPO vocabulary, which is premature at this stage.

**`detect_funding_amount` checks content up to 500 characters**
The amount signal searches both the title and the first 500 characters of content. The 500-character limit is a pragmatic tradeoff: enough to catch amounts mentioned in the article lede, without processing the full article body on every classification call. This is a tunable constant if the window needs to change.
